# GitHub Pages + Supabase migration plan

**Target:** GitHub Pages hosts the static frontend. The existing Supabase project remains the backend. Vercel is explicitly out of scope.

**Repository baseline audited:** `main` at `f1ae555c106a1ad42419a519aeac9ecd14881c88`.

## Compatibility verdict

The current Next.js application is **not deployable to GitHub Pages as-is**. GitHub Pages serves static files only. The application currently uses Next.js server runtime features:

- Server Actions in `src/app/actions/auth.ts`, `bookings.ts`, `cab.ts`, and `cms.ts`.
- API Route Handlers for Google Places at `src/app/api/places/autocomplete/route.ts` and `details/route.ts`.
- Cookie-based SSR in `src/lib/supabase/server.ts`, `src/lib/auth.ts`, and `src/proxy.ts`.
- Admin layout has `dynamic = "force-dynamic"` and server-side role checks.
- CMS media uploads use `sharp` and server-side processing.
- CMS and public page data loaders use `server-only`, React server cache, and Next cache tags/revalidation.
- Dynamic listing routes use `[slug]` segments and must be planned for static generation or client-side lookup.

Do not add `output: "export"` or enable Pages deployment until these dependencies are migrated. Doing so now will fail the build or produce non-functional forms/admin pages.

## Target architecture

- Static Next.js export generated by GitHub Actions and published using GitHub Pages Actions.
- Browser-only Supabase client using the public publishable/anon key; never put a secret/service-role key in `NEXT_PUBLIC_*`, source code, or the Pages artifact.
- Supabase Auth browser session with PKCE and a dedicated static callback page; configure allowed redirect URLs for the final Pages URL and local development.
- Direct browser database access only for operations fully protected by RLS.
- Sensitive operations (Google Places API key, booking creation, contact anti-spam/rate limiting, privileged admin operations, image processing, and any service-role work) move to authenticated Supabase Edge Functions or carefully scoped Postgres RPCs.
- Edge Functions validate the caller's JWT/role and input; use user-scoped clients/RLS for normal user operations. Service/secret keys stay in Supabase Function secrets only.
- Supabase Storage handles media persistence. Browser-side image resize/compression can replace the current Sharp-only server processing where quality/size requirements allow; otherwise use a bounded Edge Function.
- Remove Next server cache tags and `revalidatePath/updateTag`. Public CMS data should be fetched at runtime from Supabase or trigger a controlled static rebuild when SEO/static HTML needs refreshed content.

## Routing and CMS refresh decision

Dynamic `[slug]` pages need special handling. A static export cannot serve arbitrary future slugs without a generated HTML file. Preferred implementation:

1. Generate static detail pages for all published listings at build time using `generateStaticParams`.
2. On successful admin publish/unpublish/slug change, request a controlled rebuild through a protected Supabase Edge Function that triggers a GitHub Actions workflow. Keep the GitHub token in Supabase Function secrets, never in the browser.
3. Public client queries should still read current published CMS data from Supabase, with RLS limiting anonymous reads to published content.
4. Provide a not-found fallback and test direct navigation/refresh for every dynamic route.

If automated rebuild credentials are not approved, use a stable client-rendered detail route (for example, a query-based listing route) for newly created slugs until the next manual deployment. Do not promise that new pretty URLs work before a rebuild.

## Implementation sequence

### Phase 1 — Inventory and security contract
- Inventory every Server Action, API route, server-only import, cookie/header usage, redirect/revalidation call, and dynamic route.
- Export the current RLS policies, grants, functions, triggers, and Storage policies from the existing project.
- Define a role matrix for anonymous, authenticated user, host, editor, and admin.
- Verify role claims come from trusted database/app metadata, not user-editable user metadata.
- Confirm all public data policies expose only published CMS rows.

### Phase 2 — Browser Supabase/Auth foundation
- Add a single browser client factory and remove SSR cookie client/proxy dependency from the static app.
- Implement sign-in, sign-up, sign-out, password reset if present, and PKCE callback using browser auth APIs.
- Implement an auth provider/session hook and client-side route guards for UX only; database RLS/Edge Function authorization remains the security boundary.
- Add GitHub Pages and local URLs to Supabase Auth redirect allowlist.

### Phase 3 — Data and mutation migration
- Convert public CMS queries to browser-safe Supabase queries.
- Convert bookings to the existing trusted `create_booking` RPC; verify execute grants and RPC auth checks.
- Convert booking cancellation/status updates, trip plans, cab requests, contact messages, reviews, and all CMS writes to RLS-protected operations or authenticated Edge Functions/RPCs.
- Keep privileged admin actions out of direct untrusted client code; enforce role authorization server-side in Edge Functions and/or database functions.
- Move Google Places autocomplete/details behind an Edge Function and store Google API credentials as Supabase Function secrets.
- Replace Sharp upload processing with client compression or a bounded server-side Edge Function; keep Storage bucket policies least-privilege.
- Replace Next cache invalidation with runtime reads and/or the controlled rebuild trigger.

### Phase 4 — Static export and Pages workflow
- Configure Next static export, static-compatible image handling, and project-site base path.
- Remove unsupported server runtime routes/actions and dynamic rendering flags.
- Add GitHub Pages workflow: checkout, Node setup, npm ci, lint, tests, static build, upload-pages-artifact, deploy-pages.
- Restrict deploy permissions to `main`; use pinned action SHAs after verifying current releases.
- Keep CI quality checks separate from the Pages deploy workflow.
- Add `.nojekyll` if required by generated output and verify static asset paths under the repository base path.
- Pages publishing source must be set to **GitHub Actions** in repository Settings > Pages.

## Required environment/configuration

Build-time public values only:
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` or preferably the current publishable key
- `NEXT_PUBLIC_SITE_URL`

No service-role/secret key, Google server API key, or GitHub PAT belongs in GitHub Pages build output or browser variables.

Supabase dashboard:
- Auth Site URL and Redirect URLs for the exact GitHub Pages URL (and local development).
- Edge Function secrets for Google API credentials and, only if automated rebuild is selected, a narrowly scoped GitHub token.
- Review RLS, function grants, Storage policies and Edge Function CORS/JWT verification.

## Acceptance criteria

- `npm run lint`, unit/integration tests, and `npm run build` (static export) pass in GitHub Actions.
- Pages artifact contains only static assets; no server bundle, secrets, or runtime API routes.
- Direct-load and refresh work for homepage, public listing routes, login/signup/callback, dashboard, and admin.
- Auth session persists, refreshes, and signs out correctly on the Pages origin.
- Anonymous users cannot read drafts/private records or perform mutations.
- User A cannot read or mutate User B's bookings, cab requests, or trip plans.
- Only editor/admin can manage CMS; only admin can access bookings/user/audit operations.
- Booking creation uses database-derived listing price and validated capacity; illegal status transitions are rejected by the database.
- Google Places key is not present in browser network responses or static artifacts.
- Uploads, CMS edits, booking flows, and dynamic slug refresh are end-to-end tested.
- Existing Supabase data remains intact.
